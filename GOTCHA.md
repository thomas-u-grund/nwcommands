# Gotchas

The model families (nwergm, nwsaom, nwdynam, nwrem) moved to their own repositories; their gotchas
live there. Some entries below still mention them as historical examples.

Practical pitfalls specific to this repo, worth checking before you repeat them. Not a general
Stata reference — just things that have actually bitten someone working on this codebase.

## `nwsave` of a large two-mode network writes every within-mode dyad (gigabytes)

`nwsave` stores a network as an edge list made with `nwtoedge ..., ignore2mode compress`. For a two-mode network that lists all pairs of nodes *inside* each mode as well (with value 0), so `davis` (32 nodes) is 365 rows but a 5,092 x 455 network came to 2.6 GB. `ftdirectors_se.nwdta` was therefore written with a copy of `nwsave.ado` that adds `keep if <network> == 1` right after the `nwtoedge` line; `nwuse` reads such a file fine (it only needs the tie rows). Do the same when you rebuild a large two-mode data file, or fix `nwsave` to skip the zero rows of two-mode networks.

## Package manifests (`nwcommands*.pkg`) are generated — don't hand-edit them

`nwcommands-ado1.pkg`/`-ado2.pkg`/`-ado3.pkg`, `nwcommands-hlp1.pkg`/`-hlp2.pkg`,
`nwcommands-dlg1.pkg`/`-dlg2.pkg`, `stata.toc`, and `nwcommands.sthlp` are all **regenerated by
`deploy.sh`** (via `deploy_nw_build.do`) from three real source lists: `_pkg_ado.txt`,
`_pkg_hlp.txt`, `_pkg_boot.txt`. A direct edit to a `.pkg` file works *until the next `deploy.sh`
run*, which silently overwrites it from the `.txt` source list — so if you only touched the `.pkg`
file, your change quietly disappears and the real source list is left out of sync, ready to
reintroduce the exact bug you thought you'd fixed.

**When adding a new `.sthlp`/`.ado`/`.dlg` file that should ship in the public package**: add it to
`_pkg_hlp.txt`/`_pkg_ado.txt`/`_pkg_boot.txt` (whichever applies), not directly to any
`nwcommands*.pkg` file. `deploy.sh --check-only` (steps 1–3 only, no git) will tell you if
something's missing or a manifest entry points at a file that no longer exists.

Found 2026-09-05: after splitting `nwsaom.sthlp` into `nwsaom.sthlp` + `nwsaom_remarks.sthlp` (see
commit `f4e348c`), the new file was first added directly to `nwcommands-hlp2.pkg` by hand — caught
before it shipped by actually reading `deploy.sh`'s own doc comment, which names this exact failure
mode as the reason the script exists (`unw_dynam.do` missing from `lib/build.do`; `nw_syntax` and 9
other documented commands missing from every manifest — both pre-dating this file, both the kind of
drift a generated-from-source-of-truth pipeline is meant to make structurally impossible). Fixed by
adding the entry to `_pkg_hlp.txt` instead, which is what actually feeds `nwcommands-hlp2.pkg`.

This generalizes: **a companion/secondary `.sthlp` file with no matching `.ado`** (like
`nwsaom_estat.sthlp`, `nwsaom_remarks.sthlp`) is *not* caught by `deploy.sh`'s own consistency check
either — that check only flags a `.ado`/`.sthlp` pair where one half is missing from the manifests,
so a doc-only file with no `.ado` counterpart can go missing from `_pkg_hlp.txt` without the script
ever noticing. Double-check these by hand; don't rely on `--check-only` alone for a pure-doc file.

**`nwtopical.sthlp` itself is also generated** (same pipeline, `_nwdeploy.ado`'s topical-glossary
block) — the same rule applies to it as to the `.pkg` files above, and it bit twice in one session
before this was noticed. Earlier the same day, `nwtopical.sthlp`'s own `{marker}` names were found
truncated (`{marker oncept}` instead of `{marker concept}`, etc.) and hand-fixed directly in the
file (commit `b9cd002`) without realizing the file is generated, not authored. Running
`deploy.sh --check-only` afterward (while fixing the manifest issue above) silently regenerated
`nwtopical.sthlp` from `_nwdeploy.ado` and **reintroduced the exact same truncation** — the hand
edit had only patched the symptom in the build output, never the generator. Root cause, found by
actually reading the generator code: two hardcoded `substr()` offsets in `_nwdeploy.ado`, both
tuned for text shapes that no longer matched by the time they ran —
- `gen topicmarker = substr(link, 13,.)` assumed the old `nw_topical##` prefix (12 chars); the
  `nw_topical` → `nwtopical` rename shortened it to 11, so every marker name silently lost its own
  first character from that point on, and nothing errored because Stata resolves anchors by exact
  string match, not by checking they're real words.
- `local tc = substr(topic[`i'],10,.)` assumed every section number was single-level
  (`[NW-2.1] `, 9 chars through the space); a two-level number like `[NW-2.6.6] ` (11 chars, for
  the `analysis_*` subsections) lost 2 chars too few, leaving a stray `]` at the front of the
  rendered banner title.
- Along the way: `postfile ... str30 topic` silently truncated the longest real topic string
  (`[NW-2.6.6] Statistical Estimation of Networks`, 45 chars) to 30 — a fixed-width landmine
  independent of the two bugs above, only visible once they were fixed enough to reach it.

Fixed at the source (not the output) by deriving both offsets from the actual delimiters
(`strpos(link, "##")`, `strpos(topic, "] ")`) instead of hardcoded lengths, and widening the
`postfile` string widths generously. **If `nwtopical.sthlp` (or any other generated file) looks
wrong, fix `_nwdeploy.ado` and re-run `deploy.sh --check-only`, then diff the output — never hand-
edit the generated file itself, even "just this once," even under time pressure.** A hand fix to a
generated file is invisible technical debt: it looks fixed, it stays fixed until the next full
build, and then it silently isn't.

## Stata's interactive help Viewer has an undocumented size limit `type` doesn't share

`help <cmd>` (the real interactive Viewer window) and `type <file>.sthlp, smcl` (a batch/console
SMCL dump) use different rendering code paths. A `.sthlp` file large enough (`nwsaom.sthlp` hit
this at ~79KB / 1,016 lines — `nwergm.sthlp` at ~49KB did not) can render perfectly via `type` while
genuinely corrupting in the real Viewer: paragraph-boundary directives (`{p_end}`, `{pstd}`,
`{synopt:}`) start printing as literal text from a fixed point onward, and everything after it in
the document is affected, not just the section that "broke." Confirmed to be a real content-level
corruption, not just a redraw glitch — copying the garbled text out of the Viewer into a plain text
editor reproduces the same corruption verbatim.

Splitting a single huge `{synoptset}` table into several smaller ones did **not** fix this
(commit `9c208fa` — kept as a harmless structural cleanup, but confirmed by testing to be
unrelated to the actual cause). What did fix it: reducing the **whole file's total size**, by
moving long narrative/appendix material into a separate, cross-linked `.sthlp` file (commit
`f4e348c`, splitting `nwsaom.sthlp` into itself + `nwsaom_remarks.sthlp`). If a future help file
grows large and something in it starts rendering strangely in the real Viewer only, suspect total
document size before suspecting the specific content near the break point — `type`-based testing
alone will not reveal this bug at all, since it never reproduces there.

Diagnostic recipe that actually worked here (batch-mode Stata can't open the interactive Viewer at
all, so this needs a human with a real Stata session): (1) confirm `type file.sthlp, smcl` renders
clean (rules out a real markup error you could just fix); (2) have the reporter copy the garbled
Viewer text into a plain editor to confirm it's not a visual-only glitch; (3) compare total file
size against a same-package sibling that renders fine; (4) build a truncated test copy ending right
at the break point and have the reporter `view "path/to/test.sthlp"` it — if that renders clean,
it's a total-length trigger, not a content bug.

## Attaching a covariate to an `eventtime()`-declared network needs `_nwnode`, not a fresh merge

After `nwset sender receiver, eventtime(t) name(netname)` declares an event network (found while
building the `socialevolution` example dataset, 2026-09-12), the dataset left in memory is **not**
the original sender/receiver/t rows anymore — it's one row per actor who appears in at least one
event, with columns `_nwnode` (the actor's own label) and `_nwinclude`. A `merge 1:1 label using
covariates.dta` fails outright (`variable label not found`) because there is no `label` variable to
merge on at that point; the actor identifier is `_nwnode`.

The fix is a rename-merge-rename:

```
rename _nwnode label
merge 1:1 label using covariates.dta, keep(master match) nogen
rename label _nwnode
```

This is unrelated to how covariates work on an already-`nwsave()`d panel dataset (`glasgow`, `s50`,
etc.), where attributes like `smoke1`/`alcohol1` are baked into the saved network file itself and
just show up as ordinary variables on load — no merge needed there at all. The rename-merge-rename
dance is specific to attaching a covariate *after the fact* onto a freshly `nwset`-declared event
network built from a plain, not-pre-declared dataset.

## `nwset`'s own `directed` option was a complete no-op (fixed 2026-09-12)

Found while building the Stata Press book's DyNAM chapter: `nwset sender receiver, eventtime(t)
directed name(mynet)` silently produced an **undirected** network regardless of the `directed`
flag. `nwsummarize` reported `Directed: false` even though `directed` was given explicitly, no
error, no warning — `nwdynam` then rejected the resulting network outright (`nwdynam` requires a
directed network for `submodel(choice)`/`submodel(rate)`), which is what surfaced this.

Root cause: `nwset.ado`'s own `syntax` line declares `directed` as an option (alongside
`undirected`), but the local macro `` `directed' `` was never actually consumed anywhere in the
file — grep for it and it appears exactly once, in the syntax declaration, nowhere else.
Directedness for a varlist/edgelist declaration was decided **solely** by whether `undirected` was
given, forwarded to `nwfromedge` at two call sites (`nwfromedge \`varlist', ... \`undirected' ...`);
`nwfromedge` itself auto-detects directedness from the data's own reciprocity pattern whenever
neither `directed` nor `undirected` is passed to it — which is exactly what silently happened here,
since `directed` was never forwarded at all. On a small reciprocal-heavy toy event log this bit
unpredictably: a 3-row prefix of the same data correctly came out directed, but the full 10-row
version (which happens to have every dyad reciprocated at least once) auto-detected as undirected,
`directed`'s own presence in the command making no difference either way.

**Fixed** by forwarding `` `directed' `` alongside `` `undirected' `` in both `nwfromedge` call
sites in `nwset.ado` (the plain-edgelist path and the `time()`/`interval()`/`eventtime()` temporal
path). `nwfromedge` itself already had real, working logic for an explicit `directed` option — it
just never received it. Verified: explicit `directed` now sticks regardless of the data's own
reciprocity pattern; the no-flag auto-detect default and explicit `undirected` are both unchanged
(no regression) — checked against `test_nwset.do`, `test_nwset_temporal.do`,
`test_nwset_twomode.do`, `test_nwfromedge.do`, `test_nwuse.do`, `test_nwrem_ado.do`,
`test_nwdynam_ado.do`, and `test_nwsaom_ado.do`, all clean.

**Lesson**: an option present in a command's own `syntax` line is not evidence it does anything —
grep for where the resulting local macro is actually *read*, not just declared, especially for an
option that silently degrades to "no error, wrong default" rather than failing loudly.

## `nwdyadprob, undirected` doubled the tie probability (fixed 2026-09-30)

The mat()/probability-network path drew from the full matrix *before* applying `undirected`, and
the final `nwsym` OR-ed i->j with j->i, so each tie appeared with probability 1-(1-p)^2 (p = .1 gave
density .188 on 200 nodes). One draw per unordered pair now; the `density()` path was already right.

## `lib/build.do` and `deploy_nw_build.do` must be run from the repository root

Fixed in the split of the model families: both now work relative to the current directory. Run
them from the repository root (`do lib/build.do`); `lib/build.do` stops with an error if
`unw_core.do` is not found there.

## `nwmixing` on undirected networks: one-sided table and a wrong E-I index (fixed 2026-09-30)

`nwtoedge` lists each undirected edge once, so `nwmixing`'s table counted every edge in one
arbitrary stored orientation. The table was asymmetric, could drop a category entirely, and
contradicted its own "two entries for each edge" header. Worse, the E-I index summed internal
ties with `diagonal()`, which silently pairs *different* categories whenever the table is not
square (faux.mesa.high race: .025 instead of the correct -.015). The fix asks `nwtoedge` for both
orientations (`full`) when the network is undirected, and matches row and column *values*
rather than positions. The permutation p-value (`rep_EIvar()`) was never affected.

## `nwset, mat()` re-sorted the dataset under existing networks (found 2026-10-01, fixed 2026-10-01)

After `nwwebuse glasgow`, the data rows are in the networks' node order (n1, n10, n11, ...).
`nwset, mat(...) name(new)` then re-sorted the rows into n1, n2, n3, ... while the existing
networks kept their node order. Every command that reads a node attribute by row position
(`st_data(1::nodes, var)`: nwsaom `ratecov()`/`nodematch()`/`behavior()`/`present()`, nwergm
`nodematch()`/`nodecov()`, ...) then paired actors with other actors' values: `ratecov(smkc)` on
glasgow gave 0.90 before such an `nwset` and 0.12 after it.

Cause: an unlabelled network got the default labels n1, n2, ..., nN (`get_node_suffix()`), i.e.
node i of the matrix was *named* "n`i`" instead of being identified with observation i. On
glasgow those names exist but in another row order, so `_nwdatasync` (merge by `_nwnode`, then
`gsort` into the new network's node order) moved the row of "n2" (observation 12) to row 2. On
datasets whose labels are not n1..nN (gang: g1, g10, ...; s50: v1, v10, ...) the names did not
match at all and the data grew to 2N rows. The same happened with `labs()` listing the existing
nodes in another order, and with every command that declares networks through `nwset, mat()`
(nwrandom, nwring, nwsmall, nwlattice, nwexpand, nwhomophily, nwdyadprob, ...). `nwdyadprob,
density()` additionally decoded node positions from the labels ("n12" -> 12) and declared its
result on the edge list it had preserved, so its result was re-sorted on `restore`.

Fix:
- `nwset` gives an unlabelled network (no `labs()`, `labsfromvar()`, `nodenames()`, one-mode)
  of N nodes the labels of rows 1..N in row order (`nw_rowlabels_or()` in `unw_core.do`): node i
  is observation i. Otherwise the defaults n1..nN remain. (The first version of this fix required the data to have
  exactly N labelled rows; further rows may belong to networks over other nodes.)
- A new network whose labels are a permutation of the existing node set is reordered into the row
  order of the data before `_nwdatasync` (`nw_align_to_rows()`): its edge matrix, node names and
  node variable names are permuted together, so no tie changes and nothing is re-sorted.
- Both apply only while the rows are in the node order of some network in memory
  (`nw_rows_follow_net()`). After a network over a different node set has re-sorted them, the rows
  follow no network and a new network is synced as before; e.g. `nwgen x = net if _n >= 2` then
  still re-sorts the rows into `net`'s order before applying `if` (`cscripts/test_nwgenerate.do`).
- `nwdyadprob, density()` maps labels to positions through the network's node names and declares
  its result after `restore`.
- A network over a *different* node set still re-sorts (and extends) the data, as documented for
  datasync. nwsaom and nwergm now call `_nwrowalign` first: it refuses waves that list their
  nodes in different orders, and if the rows are not in the (first) network's node order it
  re-syncs them to it (attributes move with their labels) with a note
  "(data sorted into the node order of network ...)".

Test: `cscripts/test_nwset_alignment.do` (glasgow, gang, s50, lazega; every network-creating
command; nwsaom and nwergm estimates identical before and after declaring new networks).
Other commands that read attributes by row position were not audited; after declaring a network
over a different node set, `_nwdatasync netname` puts the rows back into `netname`'s node order.

## Work on `develop`, not on whatever branch is checked out (check first!)

Feature work (nwsaom, nwergm, nwrem, nwdynam, native plugins, tests, help files) happens on
**`develop`**, which the owner later merges into `main` (the release branch; `master` is an automatically synced copy kept for older links). Other branches
(for example `website-docs`) are task branches that can be many commits BEHIND `develop`.
On 2026-10-21 a whole session of nwsaom work was done on `website-docs`, 38 commits behind
`develop`, and mostly had to be discarded because `develop` already had it (varlist covariates,
native endow/creation, a much larger plugin, joint rate estimation).

Before the first edit of a session:
1. Run `git branch --show-current` and `git log --oneline HEAD..develop | wc -l`. If the current
   branch is not `develop` and `develop` is ahead, do not edit here: use a worktree of `develop`
   (`git worktree prune`, then `git worktree add <dir> develop`) or switch branches if the tree
   is clean.
2. Docs under `docs/` are gitignored and shared, so they describe `develop`'s state even when your
   checkout is older. If they name a function, option or commit that `grep`/`git cat-file` cannot
   find in your checkout, you are on the wrong branch.
3. Commit to `develop` only. Never commit to or merge into `main` (or `master`) unless explicitly asked; the release is done with `promote.sh`.
4. A stale plugin in Stata's PLUS folder shadows the repo build (see GOTCHA.md): test a rebuilt
   plugin through a scratch `adopath`.

## Mata: `A[., c + (1..p)]` is a conformability error

Inside a subscript the `..` range binds in a way that makes `A[., blk + (1..p)]` fail with 3200. Build the index
first (`ic = blk :+ (1..p)`; `A[., ic]`).

## Mata: `C.x[pd] = &(local)` stores a pointer to the variable, not to a copy

In a loop, `ptrs[k] = &(evp)` makes every pointer point at the same variable `evp`, which holds only the last value after the loop
(the symptom: the join/leave event lists of all periods were empty, the fit ran without any events and still looked plausible).
Use `&(evp :+ 0)` (an expression is copied) or a function result. Same family: an optional class argument cannot be declared
`class X scalar` (error 3000 "class scalars may not be received as optional arguments"); declare it `| class X Gout`.

## Stata: `"$NAME"` does not read an environment variable inside a do-file run with `-e`

Use `local v : environ NAME` to read an environment variable (e.g. to parameterise a dev script from the shell).

## Stata `syntax` flag options that start with "no" lose the prefix

`syntax [, NOMPLECHECK]` creates the local `mplecheck`, not `nomplecheck`; testing `"`nomplecheck'" == ""` is then always true.
Use a string option (`mplecheck(on|off)`) or a name that does not start with "no".


## Neighbor order depended on the session: Mata `order()` is not stable (fixed 2026-10-24)

`set_edge_from_triplets()` (used by `nwfromedge`, `nwset` with an edge list, `nw2project`, `nwattime`) built the CSR with
`order(ego, 1)`. Mata's `order()` does not keep the input order of tied keys, and the tie order varied with the session
(memory/sort state, e.g. after another network had been loaded), so `neighbors(i)` returned a node's neighbors in a
different order from session to session. `build_reverse_index()` had the same problem (`order(colidx, 1)`). It changed
the starting edge list of seeded MCMC fits (nwergm `seed()`). The dense path (`build_sparse_index()`) was always sorted.
Fix: sort by one combined key `ego*(n+1)+alter` (and `target*(n+1)+source` for in-neighbors), so every adjacency list is
ascending with no per-call sort. **Lesson:** never rely on the tie order of `order()`/`sort()`; add the tie-breaking
column to the key. Test: `cscripts/test_core_neighbor_order.do`.


## nwinstall deleted profile.do: `c(adopath)` contains quotes, never put it in a `shell` line (fixed 2026-10-24)

`nwinstall, remove` (also `gui`/`permanently` with an existing profile.do) erased the user's profile.do, then ran
`shell export PATH="...`c(adopath)'..."; mv ...` to put the edited copy back. After `adopath ++ "dir"` the macro
`c(adopath)` holds compound-quoted entries (`"dir";BASE;SITE;...`), so the shell saw an unbalanced quote
(`zsh: unmatched "`, `parse error in command substitution`), `mv` never ran, and the original was already gone.
`shell` does not return the command's exit code, so Stata reported rc=0. `cscripts/test_nwinstall.do` failed only
because it ran with such an adopath entry. Fix: no `shell` for file edits; write a temp file, verify it, back up, replace
with Stata's `copy`, restore on failure. **Lesson:** never erase a file before its replacement is verified in place,
never interpolate `c(adopath)`/`c(pwd)`/paths into a shell string, and prefer Stata's `copy`/`erase`/`mkdir` over `shell`.
Also: subprograms of an ado-file are not callable from a do-file (the test defines its own line counter).

## Big networks: never put per-node lists in a Stata macro, and "sparse-native" ends where a helper touches the dense matrix (fixed 2026-10-24)

`nwfromedge` was documented as proven at 100,000 nodes / 1,000,000 ties, but in Stata/BE it failed with
`r(920)` (macro substitution results in line that is too long) from about 40,000 nodes and with the
dense-matrix refusal `r(484)` at 25,000. The Mata construction (`create_by_name_sparse` +
`set_edge_from_triplets`) was never the problem; everything *around* it was:

- **BE's maximum macro length is 264,408 characters.** Any `st_local`/`st_global` of "all node labels"
  (`_nwsyntax`'s `labs`, `nwname`'s `r(labs)`, `nwsync`'s `r(vars)`, a `forvalues` loop that appends a
  label per node) breaks the first time a later line expands it. Pass lists through Mata variables
  (`putmata`/`getmata`) and use `nw_labs_string()` where a macro is unavoidable (it returns "" above
  200,000 characters; callers that need a label read it from Mata).
- **A single helper can silently turn a sparse network dense.** The usual suspects were `isview(*get_matrix())`
  in `nwload`, `check_symmetry()`/`symmetrize()` (auto-symmetrize in `nwfromedge`), `get_missing_edges()`
  and `get_selfloops_number()` (called by every `nwname`). Test with `p->is_dense_built()` after the
  command: it must still be 0. `cscripts/test_nwfromedge_large.do` does this.
- **Quadratic Mata idioms hide in small-network tests**: `result = result + ...` string building
  (`get_modes_labeled_string`, 1.5 s per `nwname` call at 40,000 nodes), `queue = queue[2::n]` as a BFS
  pop (`calculate_components`, 27 s at 100,000 nodes), all-pairs duplicate-label checks. Profile with
  `timer on/off` around stages and Mata `timer_on()`, not by reading the code.
- `selectindex()` of a 1x1 or empty condition returns a ROW vector, `1::0` is the vector (1,0), and Mata
  passes arguments by reference (assigning to a function argument changes the caller's variable).
  All three bit the sparse `symmetrize` while it was written.
- In a git worktree `lib/lnwcommands.mlib` is not on the adopath of a plain Stata session; load the core
  with `do unw_core.do` from the worktree root (what every cscript does) and put the worktree on the
  adopath explicitly. Parallel test runs that share one PLUS directory can collide while an ado such as
  `gsample` is being installed (a one-off `r(499)` in `test_nwhomophily`); rerun before suspecting code.
- `nwtoedge` built the full N x N list of dyads in `get_edgelist()` even with `compress` (so `nwsave` was
  refused above 20,000 nodes, after a minute or two). `nwtoedge, compress` of ONE network now uses
  `get_edgelist_sparse()`, which must list exactly the non-zero cells of `get_edgelist()`: that is only
  true if the dense matrix holds no missing cell besides the blanked diagonal (a cleaned two-mode network
  does), which `edgelist_sparse_ok()` checks. Several networks at once need the zero cells for the merge
  and still go through the dense list. Other limits met on the way: a Stata characteristic holds at most
  67,784 characters (the isolate list in `_dta[nwtoedge_nodes]`), `st_sdata()`/`st_sstore()` and strL are
  the way to move long strings, and `set_modes_from_labeled_string()` was O(n^2).
- An `.ado` file's extra programs (`_nwimport_edgelist` in `nwimport.ado`) are private to that file: a
  cscript cannot call them directly, only through the command.

## Scaling audit harness (`tools/scale_audit/`): three measurement traps

- **An empty scratch PLUS used to make some commands download packages (fixed).** `nwdyadprob` (and
  `nwhomophily` through it) `ssc install`ed gsample and moremata, `nwplot` labellist, `nwtabulate` tabplot, on
  first use (about 20 s, needs internet, wrote to the user's PLUS). Gone: `gsample` is replaced by the built-in
  `_nwgsample.ado` (same algorithm and same random-number stream as `gsample ..., wor`: random order via
  `uniform(N,2)`, then systematic sampling along the cumulated weights; verified identical samples, errors and
  RNG state against the real package on 300 random inputs), the `labellist` call in `nwplot`'s
  `_getvaluelabel` is a direct `st_vlload()` lookup, and `tabplot` is replaced by the built-in `_nwtabplot.ado` (the same `twoway scatter || rbar` construction; PNG and SVG exports byte-identical to the real tabplot in 24 random cases; by(), separate(), frame(), recast(), bar#() are not supported and give a clear error). Exporting a graph from a batch do-file needs an absolute path: the relative path is resolved against the log directory (`PWD`), and a failed PNG export shows as `--Break--`. `cscripts/test_no_ssc_install.do` fails if a new `ssc install` sneaks in. The harness no longer needs the
  seeded PLUS for these commands (it is harmless). Do not reintroduce `ssc install` in core code. Mata trap met
  on the way: a one-line `mata: for (...) { ... }` is "invalid expression" in Stata (braces need separate
  lines), so loops inside an ado must be vectorised or live in a compiled function.
- **`quietly` hides `display as error` messages**, so `capture quietly cmd` leaves rc 999 with no explanation
  in the log. The harness times `capture quietly cmd` and, only for a quick failure, reruns it with output on
  to read the message. `set output error` is not a substitute (it changed timings).
- **Stata `-e` puts the batch log in the directory named by the `PWD` environment variable**, not the process
  cwd. Launching from Python with `cwd=d` but an inherited PWD wrote `audit.log` into the repo root and the
  do-file was not found. Set `env PWD=d` as well.

## Native combinatorial kernels (`native/nwcomb.h`, `nwcomb2.h`): things that cost time to find

- **Mata `sort()` on one key breaks ties at random**, using the random-number stream, so the result depends on
  the RNG state at that moment (confirmed: the same 12 numbers sorted after `rseed(1)`, `rseed(2)` and after
  100 x 100 `runiform()` give three different orders of the tied rows). `Factions()` seeded its partition from
  `sort((1::n, deg), -2)`, so `nwfactions` gave different partitions on identical calls whenever two nodes had
  the same degree, and no old-vs-new comparison could be exact. Sort with a second key (`(-2,1)`: node number)
  whenever ties are possible and the order matters.
- **`_nwsyntax` clears `r()`.** In a cscript, read `r(...)` into a local or Mata variable before the next
  `_nwsyntax`; `st_numscalar("r(x)")` then returns a 0x0 void and the assertion fails far from the cause.
- **`st_numscalar()` of a scalar that does not exist returns a void, not a missing**: assigning it to a vector
  element is a conformability error. `nwg_scalar()` wraps it.
- **`strofreal(x)` without a format keeps 9 significant digits** (`nwmotifs` cut every count above 999,999,999,
  i.e. from about 800 nodes on, when it passed them through `st_local`). Use `strofreal(x, "%21.0g")`.
- **Stata's `comb(n,k)` is not exact** (floating point via gamma functions); compare counts with an integer
  product in a cscript. A network built with `nwfromedge` has as many nodes as distinct ids in the edge list,
  not the largest id you meant.
- **A Stata session keeps the plugin it loaded first.** `nwg_comb_ok()` probes the plugin once per session
  (external scalar `nwg_comb_state`: `.` = not probed, 1 = kernels available, 0 = use the Mata code); a
  cscript sets it to 0 to run the Mata reference and back to `.` afterwards. After rebuilding the plugin start
  a new Stata process (`rm` the file first, never `cp` over a loaded one). A stale `nwgraph_macos.plugin` in
  PLUS shadows the repo's one (the probe then finds no kernels and silently uses the slow Mata path).
- **Why the cohesion kernel may reorder flows but not change results:** the value of a maximum flow and the set of
  nodes reachable from the source in its residual graph do not depend on the order of the augmenting paths, so
  the C search (bidirectional BFS, early stop at the current minimum) returns the same minimum, witness pair and
  cutset as the Mata one; what does depend on order is only *which* equal-valued pair is found first, and the
  loops visit the pairs in the Mata order. A block certified by the parent's `k`-component step carries its exact
  connectivity and witness pair into the next level (the target search that ran to the end is the same query
  sequence as the plain connectivity search).
- **The n-clan search prunes**, it does not enumerate-then-filter: a branch is dropped when a member of `R` is
  farther than `n` steps from the newest member inside `R` + candidates (distances only grow in the subsets a
  clan below the branch can be). The scratch distance array must be all `-1` between uses; `clan_ok()` once left
  it dirty and the pruned search lost clans (found by the exact old-vs-new comparison, not by the size tests).

## Equality tests against an old implementation: set the sort seed, and do not trust `merge` order

Stata's `sort` (and so `merge`) breaks ties in a random order controlled by `set sortseed`. Two runs of the same
command can list rows with equal keys in a different order, which made old-versus-new comparisons of
`nwtoedge` with node attributes and of the Pajek/UCINET/GML exports look like failures. Set `set sortseed` before each
network in a comparison script, and where the order of a file matters sort explicitly (the exports now sort by alter
label, then ego label). Also: a native-plugin kernel that must reproduce Mata arithmetic bit for bit needs
`-ffp-contract=off` (see `native/Makefile`), otherwise fused multiply-adds change the last digits.

## Native plugin algorithm codes: keep the ranges apart

`native/nwgraph.c` dispatches on the first number of the argument string. 1-2 are betweenness and BFS distances,
3-9, 22-25 and 99-100 belong to the combinatorial kernels (`comb_handles()`; use 26 and up for the next kernel), 20 is the vertex-connectivity search
(nwkcomponents) and 21 the Kamada-Kawai iterations (nwplot layout(kk)). A range test such as 3..100 in one
feature swallows the codes of another; when adding a kernel, pick a code outside every existing range.
A Mata `v[p] = vals[g]` with a single distinct value fails (a 1 x 1 matrix cannot be indexed by a vector): guard the scalar case.

## Stata inserts a blank into long option values: never pass node labels through an option string

`syntax ..., labs(string)` (and any `command, opt(`longmacro')`) cuts a value longer than 5,292 characters: a blank is
inserted into every 5,292nd character, so a label list for 900+ nodes ("n1,n2,...") comes out with names such as
`n1 067`. The symptom is not an error: the new network has nodes the dataset does not know, `_nwdatasync` merges
and APPENDS rows (a 5,000-node network gives _N = 5,004), and a later command that needs `_N == nodes` fails
(`nwhierarchy`: "number of selected observations must match dimension of mymat"). Found at 5,000 nodes; the same
bug sat in every command that forwarded `r(labs)`/`labs` to `nwset`. Pass the names in a Mata variable instead:
`nwset ..., nodenames(<mata vector>)`; `nwrandom ..., nodenamesmata()`, `nwreplacemat ..., labsmata()` are the
forwarding options. Test: `cscripts/test_scale5k.do`. Remaining paths that still use `labs()` with a macro:
`nwexpand, network()`, `nw2set`, `nwimport` (user supplied lists; keep them below 5,000 characters or call `nwfromedge`).

## Algorithm codes 22 and 23 (triad balance, bipartite matching); kernel version 3

`native/nwcomb2.h` has `comb_balance()` (code 22) and `comb_matching()` (code 23); `comb_handles()` lists them and
`NWCOMB_VERSION` is 3. Mata asks `nwg_comb_version()`: a plugin older than 3 (Linux and Windows until CI rebuilds them)
keeps the older Mata code of `calculate_balance()` / `calculate_bipartite_matching()`. `comb_matching()` is an exact
port of the dense Edmonds-Karp (residual arcs visited in ascending node number, the augmenting path ends at the first
discovery of the sink), so it returns the same matching, not just the same size. To force the Mata path in a test,
set the external `nwg_comb_state` to 0 (see `cscripts/test_scale5k.do`).

## Equality checks of `nwdropnodes` / `nwkeepnodes`: the order of the dropped rows is not stable

The rows of dropped nodes stay at the end of the data (attributes missing) and their order depends on `set sortseed`
state, i.e. on how many sorts ran before. Compare the first `r(nodes)` rows by position and the rest as a sorted set.

## Algorithm code 24 (Louvain communities); kernel version 4; Louvain bug that hid from small networks

`native/nwcomb2.h` has `comb_louvain()` (code 24; `NWCOMB_VERSION` 4, `nwg_comb_version() >= 4` in Mata). It is an exact port of
the corrected Mata `Louvain()`: same visiting order, candidates in ascending community number, a move needs a gain larger by
more than 1e-12, communities numbered in ascending order of their old numbers. The old Mata code counted the node's own
loop (the weight inside a super-node, present from the second level on) as a tie to its own community, so super-nodes never
moved and the aggregation levels merged nothing: modularity was fine for ~1,000 nodes (the first level alone found 30
communities) and collapsed above ~1,500 (3,000 nodes: 1,311 communities, Q 0.07; the right answer is ~14 communities,
Q 0.18). No small-network test could see it because the first level already looked plausible. When you write a graph
algorithm that aggregates, check the number of communities and Q at 3,000+ nodes against an independent computation.
`cscripts/test_scale10k_louvain.do` compares native and Mata on 40 random networks and recovers a planted partition.

## `tabulate` and `matrix rownames` stop at about 1,000 groups

`tab x, matrow() matcell()` fails with r(134) ("too many values") above 1,000 distinct values in Stata/BE, and a row-name
list of thousands of tokens exceeds the command-line limit. `nwcomponents` (sparse networks have thousands of components) and
`nwcommunity` failed that way after the result was computed. Count in Mata (`sort`, `panelsetup`) and set row names with
`st_matrixrowstripe()`; tabulate for display only when there are at most 1,000 groups. Mata `sort(x, -1)` of a size table breaks ties
randomly: sort by `(-1, 2)`.

## Mata traps met in stage 2

- A function that declares `external real scalar x` CREATES x (as a missing value) when it does not exist: test existence with
  `findexternal()` first (a threshold function returned `.` and silently switched an optimization off).
- `colvector :+ rowvector` is a conformability error in Mata (only vector with matrix broadcasts): build the matrix with `J()`.
- `v[a][b]` (chained subscripts) is not allowed; a one-line `{ ...; ... }` inside `mata ... end` of a do-file is "invalid expression".
- The harness runs the checks after `quietly timer list`, which replaces `r()`: the command's results are kept with `_return hold`
  and put back with `_return restore, hold` before each check line.
- `strofreal(x)` of exact counts: compare with integer arithmetic (6 * C(n,4) = (n(n-1)/2)((n-2)(n-3)/2)), a division by 24 is not exact.

## Two-mode networks are dense by definition: 15,000 nodes cost 7 GB

`clean_matrix_2mode()` used to compare an n x n STRING matrix of modes (10 GB at 15,000 nodes); it blanks the same-mode cells in place
now. The cleaned two-mode matrix still holds missing cells, so every two-mode command works on the dense matrix (10,000 + 5,000 nodes
peak at 7 GB). `nw2toedge` without `compress` lists every pair of nodes of the two modes and is refused above 50,000,000 rows.

## The audit recipes of stages 0 and 1 measured the wrong thing in two places

`nwset from to, name(x)` is the MATRIX form (two variables = a 2 x 2 matrix) and took 0.05 s at every size; the edge-list form is
`nwset from to, edgelist name(x)`. `nw2fromedge` was fed `to` in 1..N, i.e. N + N nodes, not N + N/2. Both recipes are corrected in
`tools/scale_audit/spec.py` (a recipe that "passes" at every size deserves a look at what network it actually built).


## Scaling audit, stage 3 (20,000 nodes): what cost time to find

- **The peak memory of a harness row includes the correctness check.** `/usr/bin/time` measures the whole Stata process: the
  generator, the timed command and the check that follows. Several rows of the first 20,000-node run said MEMORY_KILLED for
  commands that had finished (`nwgeodesic` 49 s, `nwreplacemat`, `nwtranspose`): the check built the tie index of a dense
  3.2 GB result. The harness now prints `NWAUDIT_CMD_RC` when the command returns, reports a kill after that as OK with
  `correct = UNCHECKED (the check exceeded the memory cap)`, and `nwa_net()` counts the ties of a big dense result row by row.
  A kill before `NWAUDIT_SECS` is a real kill of the command.
- **Mata `sum(M :== .)`, `sum(M :!= 0 :& M :!= .)`, `edge' ...` on an n x n matrix each hold one n x n temporary per operator**
  (8 bytes a cell: 3.2 GB at 20,000 nodes). `missing(M)` counts the missing cells without a temporary; a row-by-row loop
  (`for (i...) sum(M[i,.] :== ...)`) replaces the others. `x = y` of an n x n matrix is a copy: `swap(x, y)` moves it
  (`ensure_dense_built()`, new `set_edge_take()` used by `nwset`). The old dense `build_sparse_index()` held the matrix, its
  copy, a mask and two more temporaries (four matrices) just to find the non-zero cells.
- **`selectindex(col :== j)` without a match is a 0 x 1 matrix, so `cols(idx) > 0` is true.** `edge_weight(i, j)` indexed
  `idx[1]` of it and stopped with a subscript error (swallowed by a `capture`: `nwvalue` returned `.` for every pair without a
  tie once it used the sparse index). Test `rows(idx) * cols(idx) > 0`.
- **A Mata function that assigns to its argument changes the caller's variable.** `rep_EIvar()` of `nwmixing` did
  `net1 = (net1 :!= 0)` on `*netobj->get_matrix()`: after `nwmixing, permutations()` a valued network held only its 0/1
  pattern. The same file's `rep_EIattr()` read `net1 != .` (no colon: ONE comparison, true) so the missing diagonal counted
  as ties in every permutation of `nwtabulate, attribute()`. Both fixed; every `:`-less comparison in a Mata one-liner is
  worth a look.
- **`rdiscrete()` accepts at most 10,000 probabilities** ("exceeded maximum table size of 10000", r(3300)); `nwpref` used it
  with a vector of n probabilities and stopped above 10,000 nodes. Above that size a pick proportional to the degrees is a
  uniformly chosen end point of the ties made so far.
- **Quadratic code that looked like bookkeeping**: `update_nodesvar()` compared all pairs of variable names (9 s at 10,000
  nodes, on every `nwnoderename`), `build_edge_value_matrix()` searched the list of all nodes for every tie
  (`nwset, time()` did not finish at 20,000 nodes), `nw_community_denserelabel()` searched all communities for every node,
  `nwattime` walked all n^2 cells in Mata. A run of "OK slow" rows that quadruple from 10,000 to 20,000 nodes is the
  signature.
- **A command that builds its result with `nwset, mat()` holds three n x n matrices at once** (the caller's, the copy for the
  network, the one inside `set_edge()`); now two. `nwsym`/`symmetrize()` of a dense matrix held five; it works pair by pair
  above 2,000 nodes. `nwname` called `sum(M :== .)`, which held a third.
- **Random generators**: `runiform(r, c)` fills row by row, so drawing the rows in blocks gives the numbers of one big call
  (this keeps `nwrandom, prob()` identical to the matrix version at any size). `nwrandom, density()` shuffled all n^2 cells;
  above 5,000 nodes the positions of the ties are drawn directly (a different stream, the same distribution); up to 5,000
  nodes the old shuffle runs, so earlier seeds still give the same networks.
- **A prefix `external` declaration creates the external** (see stage 2): `nw_sparse_min_nodes()` reads the test switch
  through `findexternal()` and a pointer, without declaring it.
- **`nwclique` stored every maximal clique, size 1 and 2 included**, as a row of n zeros and ones: a sparse network has about
  as many maximal 2-cliques as ties, 100,000 rows of 20,000 numbers (77 s at 10,000 nodes, killed at 20,000). Only the
  cliques of the asked size are kept now (0.9 s and 2.9 s).
- **A Mata `sort()` / `uniqrows()` / `order()` advances the state that breaks ties in the Stata sorts that follow** (the random-number stream
  itself is not touched: `runiform()` after it is the same). The visible effect is the order of the data rows that belong to no node
  (the leftover rows when a smaller network follows a larger one): the old-versus-new comparison of `nwrandom` and `nwnoderename` differed
  in `_nwnode[10..22]` after `update_nodesvar()` got a `uniqrows()`; the hash version of the duplicate test leaves them identical. In a
  comparison script compare those rows as a sorted set (see the `nwdropnodes` entry) or avoid a sort on a path every command takes.
- **The generator `nwpref` picks from the ties made before the new node**: a stub list that grows while the node picks lets the node pick itself
  (found by `test_scale20k.do` counting the ties of a 12,000-node network).
- **Plugin and Mata must agree on the call**: the block call of the distance kernel (`2 n directed nties source nblock`) is used only when
  `nwg_comb_version() >= 5`; an older plugin ignores the extra number and would fill one column only, silently. Rebuild the plugin
  (`rm`, then `make -C native macos-nwgraph`) BEFORE running anything that loads the new `unw_core.do`; the harness picks up files the moment they
  are edited, so do not edit the worktree while an audit runs (a run in the window between the edit and the rebuild had to be discarded).

## Scaling audit, stage 4 (100,000 nodes): what cost time to find

- **`encode` stops at 65,536 distinct strings.** `nwcompressobs` tried `encode` on every variable and, when it failed, compared the
  variable with `.`: for the node labels of a network with more than 65,536 nodes that is a string compared with a number
  (r(109) "type mismatch"). `nwdropnodes`, `nwkeepnodes`, `nwdrop`, `nwkeep`, `nwsubset` and `nwreplace` all end in
  `nwcompressobs`; none of them worked above 65,536 nodes, and the audit showed the failure only as "OTHER_ERROR" with a late
  re-run message ("Network dn already exists"): the first run had created the network, the second showed the error that does not
  say what failed. Test strings with `confirm string variable`, never with `encode`. Look for the same pattern in `nwexpand`
  (`encode` of a string attribute) before trusting it above 65,536 distinct values.
- **A quiet re-run hides the first error, a noisy one can hide the message of a guard.** `display "{err}..."` inside `quietly` prints
  nothing (the guards of stage 3 were called outside `quietly`); `display as error "..."` always prints. `_nwdenseguard` and
  `_nwtimeguard` use `display as error`.
- **`nwset, time()` and `interval()` built n x n matrices of times** (80 GB each at 100,000 nodes; killed at 20 GB before the
  command even started, so the audit row of `nwattime` said MEMORY_KILLED for a recipe whose *pre* step was the culprit). Above
  2,000 nodes the times are kept as a list (ego, alter, value) sorted by ego and alter (`build_edge_value_triplets()`,
  `nw_triplet_values()`, flag `timesparse`); `get_edge_time()`/`get_edge_start()`/`get_edge_end()` then return that list, not a
  matrix. Any new reader of those three getters must test `get_time_sparse()` first. Two-mode temporal networks keep the matrices.
- **A Mata function that uses a class must come after the class definition in `unw_core.do`** ("function ... not declared in
  class" otherwise); `nw_set_temporal_values()` therefore sits next to `nw_ties_only()`, not next to `build_edge_value_matrix()`.
- **`keep_nodes()`/`drop_nodes()` called `ensure_dense_built()`**, so every `nwdrop ... if` of a large network failed with the dense
  refusal; a network held as stored ties is now renumbered tie by tie. Compare with the dense route by calling `get_matrix()` first
  (it makes `edge_dense_built` true).
- **`value_counts_to_vars()` has a 2,147,483,647 limit that only `tabulate [fweight=]` needs.** `nwrecode` only sums the counts and
  passes `fwlimit = 0`; `nwtabulate` writes the table itself above the limit. Do not move the check back into the Mata function.
- **Time guards use measured rates, not a theory.** `_nwtimeguard` (model `bfs`: seconds = nodes x 2 x ties / rate; model `power`:
  seconds = base x (nodes/20000)^exponent). The rates come from the 20,000-node run (closeness 8.1e8 tie visits per second) corrected
  by the single 100,000-node run that was allowed 1,500 seconds (302 s, rate 6.6e8: cache misses). If a command gets faster, change
  the rate in the command's `_nwtimeguard` call, nowhere else. Limit: `nw_max_seconds` in `unw_defs.ado` (120).
- **A recipe whose argument is the n x n matrix cannot be guarded** (`nwdyadprob, mat(J(N,N,.01))`: Mata builds 80 GB before the command
  starts); the recipe is capped at 20,000 in `spec.py`.
- **`pgrep -f run_audit` finds the shells that wait for it.** A wait loop `until ! pgrep -f run_audit...` never ends while another
  session's wait loop (whose command line contains the same words) exists; match `ps aux | grep "[r]un_audit.py --sizes N" | grep -v zsh`.

## `mata mlib index` does not persist: a library installed by net install can be missing from a session's Mata library list

Stata builds its list of Mata libraries (.mlib) once, early in a session; `mata mlib index` rebuilds it for the running session only
and nothing is saved. A library that `net install` put into PLUS/l/ can be absent from the list (`mata mlib query` shows `lnwcommands`
but not `lnwsaom1, lnwergm, ...`). The first Mata call then stops with r(3499) "<function>() not found", and a Mata block that mentions a class of
the library stops the whole ado file with r(3000) "class ... undefined (error occurred while loading ...)". Running `mata mlib index`
by hand "fixes" it for that session only, which hid the bug in every manual test.
- Every entry program of the model packages starts with `_<pkg>_libcheck` (which runs `mata mlib index` once when a library function is not visible); do not
  call Mata before it.
- A **file-scope** `mata:` block in an .ado file is compiled when the file is auto-loaded, i.e. before any program of the file runs:
  `_<pkg>_libcheck` is therefore also called at file scope (`capture quietly ...`) in front of such a block.
- Reproduce: `SMOKE_STALE=1 tools/smoke_fresh_install.sh [core_dir model_parent_dir]` builds exactly this state (the session's Mata
  index is made while only the core library is visible). Without `SMOKE_STALE` a plain new session usually finds all libraries,
  which is why a simple "install, restart, run" test passes.
- `nwinstall, all` and `nwinstall, models` run `mata mlib index` after installing; the model packages do not rely on it.
